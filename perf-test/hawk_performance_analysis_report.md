# 内外网穿透网关性能测试报告

## 1. 测试概述

本次测试针对内外网穿透网关系统进行压力测试，目的是评估系统在不同负载下的性能表现，识别性能瓶颈点并提供优化建议。

### 1.1 测试目标
- 评估系统当前性能水平
- 识别系统性能瓶颈
- 为后续优化提供数据支撑

### 1.2 测试范围
- API接口响应性能
- 并发处理能力
- 系统稳定性及错误处理能力

## 2. 系统架构

### 2.1 架构概览
```
┌─────────────────────────────────────┐     ┌─────────────────────────────────────┐
│         机器 A（外网）               │     │          机器 B（内网）              │
│         192.168.123.66              │     │          192.168.123.81             │
├─────────────────────────────────────┤     ├─────────────────────────────────────┤
│                                     │     │                                     │
│  应用服务:                           │     │  应用服务:                           │
│  ├─ scp0005 (外网网关)      :8080   │     │  ├─ scp0006 (内网穿透)      :8082   │
│  └─ outer-consumer          :8081   │     │  └─ target-service          :8017   │
│                                     │     │                                     │
│  数据库:                             │     │  数据库:                             │

│                                     │     │                                     │
│  中间件:                             │     │  中间件:                             │
│  ├─ Redis                   :6379   │     │  ├─ Kafka                   :9092   │
│  ├─ Kafka                   :9092   │     │  └─ Canal (CDC)            :11111   │
│  ├─ Canal (CDC)            :11111   │     │                                     │

│                                     │     │                                     │
└─────────────────────────────────────┘     └─────────────────────────────────────┘
```

### 2.2 数据流转路径
1. 客户端 → scp0005 (机器A外网网关)
2. scp0005 → INSERT → 机器B的MySQL(请求表)
3. 机器B的 Canal 监听 Binlog → Kafka (inner_request_binlog)
4. scp0006 消费 Kafka → 调用 target-service
5. scp0006 → INSERT → 机器A的MySQL(响应表)
6. 机器A的 Canal 监听 Binlog → Kafka (outer_response_binlog)
7. outer-consumer 消费 → 写入 Redis
8. scp0005 从 Redis 获取结果 → 返回客户端

## 5. 性能分析

### 5.1 关键发现

1. **吞吐量瓶颈明显**: 系统QPS被限制在11左右，即使大幅增加并发数也无法提升吞吐量
2. **延迟随负载递增**: 平均延迟从轻载的858ms增长到重载的1.58s
3. **高并发下稳定性差**: 并发数超过50后，错误率急剧上升
4. **系统容量有限**: 极限测试下系统完全不可用

### 5.2 性能特征分析

**吞吐量平台化**: QPS在11左右达到上限，表明系统存在固定的处理能力上限，这通常是由于以下原因造成的：
- 单线程处理逻辑
- 外部依赖资源限制（如数据库连接池、消息队列消费者数量）
- 系统内部锁竞争

**延迟递增**: 随并发数增加延迟显著上升，这是典型的系统过载征象，表明系统在高负载下无法有效处理请求。

**错误率激增**: 高并发下错误率急剧上升，说明系统缺乏有效的流量控制和降级机制。

## 6. 瓶颈分析

### 6.1 主要性能瓶颈

#### 6.1.1 消息队列处理能力
- **问题**: Kafka消息处理链路存在处理瓶颈
- **证据**: QPS被限制在11左右，远低于传统Web应用的处理能力
- **影响**: 高并发下消息积压导致超时

#### 6.1.2 CDC (Canal) 组件延迟
- **问题**: Canal监听binlog并发送到Kafka存在延迟
- **证据**: 数据流转链路长，每个环节都有延迟累积
- **影响**: 高并发下binlog解析和传输成为瓶颈

#### 6.1.3 数据库I/O性能
- **问题**: 两次数据库操作（请求表和响应表）增加了整体延迟
- **证据**: 延迟随并发数增加显著上升
- **影响**: MySQL在高并发写入时可能出现锁竞争和性能下降

#### 6.1.4 网络延迟累积
- **问题**: 双向网络通信及多次网络调用增加总体延迟
- **证据**: 跨机器通信引入额外延迟
- **影响**: 每个环节都可能引入网络延迟

### 6.2 架构层面瓶颈

#### 6.2.1 同步阻塞模式
- **问题**: 整个数据流转过程采用同步模式
- **影响**: 客户端必须等待整个流程完成后才能收到响应

#### 6.2.2 多跳通信
- **问题**: 请求需要经过多个组件处理
- **影响**: 每一跳都会增加延迟，且任一环节故障都会影响整体可用性

## 7. 优化建议

### 7.1 短期优化措施

#### 7.1.1 消息队列优化
- **调整Kafka分区数量**: 增加分区数以提高并发处理能力
- **优化消费者组配置**: 增加消费者实例数，提高消费能力
- **调整Kafka参数**: 优化batch.size、linger.ms、acks等参数

#### 7.1.2 CDC组件优化
- **调优Canal配置**: 调整batchSize、fetchSize等参数
- **使用批量处理**: 减少网络交互次数
- **评估Canal HA配置**: 提高可用性和性能

#### 7.1.3 数据库优化
- **优化表结构和索引**: 确保关键字段有合适的索引
- **调整连接池参数**: 增加最大连接数，优化超时设置
- **考虑读写分离**: 减轻主库压力

### 7.2 中长期架构优化

#### 7.2.1 异步处理模式
- **引入异步响应机制**: 对于非实时性要求高的请求，可以采用异步模式
- **实现回调机制**: 减少同步等待时间

#### 7.2.2 缓存优化
- **优化Redis访问**: 使用连接池，减少连接开销
- **引入本地缓存**: 减少对远程缓存的依赖

#### 7.2.3 服务拆分与微服务化
- **解耦核心服务**: 将不同功能模块独立部署
- **实现熔断降级**: 提高系统容错能力

#### 7.2.4 流量控制
- **实现限流机制**: 防止系统过载
- **增加熔断保护**: 在下游服务异常时快速失败

### 7.3 监控与运维优化
- **增加全链路监控**: 追踪每个环节的处理时间
- **设置性能阈值告警**: 及时发现性能问题
- **定期性能回归测试**: 确保优化效果可持续

## 8. 结论

内外网穿透网关系统当前存在明显的性能瓶颈，主要表现为：

1. **吞吐量上限**: 系统QPS被限制在11左右，无法满足高并发需求
2. **高延迟问题**: 平均延迟高达858ms以上，在高并发下更严重
3. **稳定性不足**: 高并发下错误率急剧上升，系统可用性差

系统的主要瓶颈集中在消息队列处理链路、CDC组件延迟、数据库I/O操作以及架构层面的同步阻塞模式。建议优先实施短期优化措施以快速改善性能，同时规划中长期架构优化以从根本上解决问题。
