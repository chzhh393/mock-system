# WebFlux Sinks + HTTP 回调优化性能测试报告

**测试日期**: 2026-01-15
**测试分支**: `feature/async-sinks`
**测试环境**: local-e2e (Docker Compose)

---

## 1. 优化概述

### 1.1 优化目标
将 scp0005 等待响应的机制从 **Redis 轮询** 改为 **WebFlux Sinks + HTTP 回调**，减少轮询开销，提升系统吞吐量和稳定性。

### 1.2 技术方案

**优化前（Redis 轮询）**:
```
客户端请求 → scp0005 写入DB → 轮询Redis等待结果（每50ms一次）→ 返回响应
```

**优化后（HTTP 回调）**:
```
客户端请求 → scp0005 写入DB → Sinks.One 异步等待 → outer-consumer 回调通知 → 返回响应
```

### 1.3 代码变更

| 文件 | 变更类型 | 说明 |
|-----|---------|------|
| `PendingRequestManager.java` | 新增 | Sinks.One 管理器，存储待处理请求 |
| `CallbackController.java` | 新增 | HTTP 回调接口 `/internal/callback/{requestId}` |
| `CallbackService.java` | 新增 | 异步回调发送服务（线程池） |
| `GatewayService.java` | 修改 | 替换 `pollRedisResult()` 为 `pendingRequestManager.waitForResult()` |
| `BinlogConsumer.java` | 修改 | 添加回调调用 |
| `application.yml` | 修改 | 添加回调配置 |

## 4. 延迟分布分析

### 4.1 单次请求耗时分解

通过日志追踪单次请求的耗时分布：

```
时间线示例:
├── 15:59:57.577  请求开始
├── 15:59:57.604  注册 Sinks 等待 (+27ms)
├── 15:59:57.892  写入内网数据库 (+288ms)
│   ↓
│   [CDC 同步延迟 ~4秒]
│   ↓
├── 16:00:02.059  收到回调 (+4167ms)
├── 16:00:02.066  请求完成 (+7ms)
└── 总耗时: 4489ms
```

### 4.2 延迟组成

| 阶段 | 耗时 | 占比 |
|-----|------|------|
| 请求处理 + DB写入 | ~300ms | 7% |
| CDC 同步（内网→外网） | ~4000ms | **89%** |
| 回调处理 | ~200ms | 4% |

**结论**: CDC 同步延迟是主要瓶颈，占总延迟的 89%。

## 5. 分析与结论

### 5.1 优化效果

| 场景 | 效果 | 说明 |
|-----|------|------|
| **轻载（10并发）** | 略有下降 | 回调机制引入额外 HTTP 调用开销，在低并发时相对明显 |
| **中载（30并发）** | 明显改善 | TPS +3%，延迟 -2.8%，超时 -100% |

### 5.2 主要收益

1. **稳定性提升**: 超时数从 23 降到 0，系统在高并发下更稳定
2. **资源节省**: 消除了 Redis 轮询的 CPU 和网络开销
3. **响应更及时**: 回调机制可以第一时间通知结果，无需等待轮询间隔

### 5.3 未达预期原因

原计划预期延迟减少 90%+，实际只减少 2.8%，主要原因：

1. **CDC 延迟占主导**: 约 4 秒的 CDC 同步延迟是不可避免的
2. **轮询开销本身不大**: 原轮询间隔 50ms，在 4 秒总延迟中占比很小
3. **回调引入新开销**: HTTP 回调本身也有网络延迟

### 5.4 进一步优化建议

若需进一步提升性能，应关注 CDC 延迟优化：

| 优化方向 | 预期效果 | 复杂度 |
|---------|---------|--------|
| 减少 Canal 批量间隔 | 减少 500-1000ms | 低 |
| 优化 Kafka 消费配置 | 减少 100-200ms | 低 |
| 使用 Debezium 替代 Canal | 可能减少 1-2s | 中 |
| 直接内存通信（同机部署） | 减少 2-3s | 高 |
