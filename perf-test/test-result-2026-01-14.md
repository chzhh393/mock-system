**测试时间**: 2026-01-14
**测试环境**: Canal CDC (192.168.123.66 ↔ 192.168.123.81)

## 各环节耗时分析

基于日志采样：

| 环节 | 实测耗时 | 状态 |
|------|----------|------|
| 目标服务 (target) | 58-63ms | ✓ 正常 |
| scp0006 处理 | 71-160ms | ✓ 正常 |
| outer-consumer 处理 | 1-5ms | ✓ 正常 |
| 数据库写入 (inner) | ~15ms | ✓ 正常 |
| 数据库写入 (outer) | 10-100ms | ⚠ 波动较大 |
| Canal CDC 批处理 | ~100ms/批 | ✓ 正常 |

---

## 瓶颈分析

### 1. 主要瓶颈: TPS 天花板 (~12 req/s)

- **现象**: 并发从 5→10→20，TPS 仅从 9.11→11.43→11.75
- **原因**: 系统串行处理能力受限

### 2. 次要瓶颈: 延迟随并发线性增长

- **现象**: 5并发: 434ms → 10并发: 859ms → 20并发: 1620ms
- **原因**: 请求排队等待处理

### 3. 潜在问题: 外网数据库写入延迟波动

- **现象**: 写入延迟 10-100ms，波动较大
- **可能原因**: 网络延迟或数据库负载

---

## 延迟分布估算

在高并发下(20并发)，总延迟 1620ms 分布：

```
数据流处理: ~300ms
├── 内网 CDC 延迟: ~100ms (Canal 批处理周期)
├── scp0006 处理: ~100ms (含目标服务60ms)
└── 外网 CDC 延迟: ~100ms (Canal 批处理周期)

排队等待: ~1300ms (系统处理能力不足)
```

---

## 优化建议

### 高优先级: 提升 TPS 上限

- 增加 scp0006 Kafka 消费并发数 (当前 concurrency=3)
- 增加 outer-consumer Kafka 消费并发数

### 中优先级: 降低 CDC 延迟

- 调小 `canal.mq.canalBatchSize` (50→20)
- 调小 `canal.mq.canalGetTimeout` (100→50)

### 低优先级: 优化 Redis 轮询

- 减小 `poll-interval-ms` (100→50)
- 或改用 Redis Pub/Sub 机制

---

## 结论

| 指标 | 当前值 | 目标值 |
|------|--------|--------|
| 最大 TPS | ~12 req/s | >20 req/s |
| 低负载延迟 | 400-500ms | <400ms |
| 高负载延迟 | 1.6s+ | <1s |

主要瓶颈在于**系统串行处理能力**，需要提升 Kafka 消费者并发数来突破 TPS 天花板。
