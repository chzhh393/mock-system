# 并发连接数测试报告

**测试时间**: 2026-01-19
**测试目的**: 评估轮询模式下网关的并发连接处理能力
**测试环境**: Canal CDC (192.168.123.66 ↔ 192.168.123.81)

---

## 一、测试背景

### 问题
之前测试显示 20 并发下 TPS 仅 63，需要验证：
1. 是否因为并发数太少导致 TPS 低？
2. 轮询模式的并发上限是多少？

### 测试模式
- **scp0005**: WebFlux + Redis 轮询等待
- **scp0006**: Spring MVC + 异步线程池 (20核心/50最大)

---

## 三、性能分析

### 3.1 并发数对 TPS 的影响

```
50ms 延迟下并发增加效果：

20 → 100:   TPS 63 → 251   (+299%, 4x 提升)
100 → 500:  TPS 251 → 587  (+134%, 2.3x 提升)
500 → 1000: TPS 587 → 598  (+2%, 基本见顶)

结论：增加并发可以提升 TPS，但存在上限
```

### 3.2 延迟对 TPS 的影响

| 延迟 | 500并发 TPS | 响应时间 |
|------|------------|---------|
| 0ms | 790 | 518ms |
| 50ms | 587 | 478ms |

```
响应时间组成分析：

0ms 延迟:  链路固有延迟 ≈ 265ms
50ms 延迟: 链路固有延迟 + 50ms ≈ 315ms

链路固有延迟包括：
- MySQL 写入 (R2DBC)
- Canal CDC 同步
- Kafka 传输
- scp0006 处理
- 响应写入外网 MySQL
- Canal CDC 同步
- outer-consumer 写入 Redis
- scp0005 轮询 Redis (100ms 间隔)
```

### 3.3 轮询模式的瓶颈

```
轮询模式资源占用：

每个请求生命周期：
┌─────────────────────────────────────────────────────┐
│ 连接建立 → 写入MySQL → 轮询Redis → 返回响应         │
│     ↑          ↑           ↑                        │
│   HTTP连接   R2DBC连接   Redis连接                  │
│   (占用)     (占用)      (持续轮询)                 │
└─────────────────────────────────────────────────────┘

瓶颈点：
1. R2DBC 连接池: 20
2. Redis 连接池: 20
3. 轮询间隔: 100ms (每秒最多 10 次轮询/连接)
4. Netty EventLoop 被轮询任务占用
```

---

## 四、关键结论

### 4.1 并发数的影响

| 结论 | 说明 |
|------|------|
| **63 TPS 确实因并发太少** | 20 并发 → 500 并发，TPS 从 63 → 587 (9x 提升) |
| **最佳并发数: 500** | 超过 500 后 TPS 不再增长，超时开始增加 |
| **轮询模式上限: ~600 TPS** | 受限于轮询机制和连接池资源 |

### 4.2 轮询模式 vs 异步模式对比

| 指标 | 轮询模式 | 异步模式 (预期) |
|------|---------|----------------|
| 最大 TPS (50ms延迟) | ~600 | 1000+ |
| 最佳并发数 | 500 | 1000+ |
| 资源效率 | 低 (持续占用) | 高 (事件驱动) |
| 连接利用率 | ~1-5% | ~50%+ |

## 七、后续优化方向

1. **scp0005 改成 Redis Pub/Sub 异步模式**
   - 预期 TPS 提升至 1000+
   - 连接利用率大幅提高

2. **增加连接池大小**
   - R2DBC: 20 → 50
   - Redis: 20 → 50

3. **减少轮询间隔** (临时方案)
   - 100ms → 50ms
   - 代价：Redis 负载增加



  轮询模式性能指标（50ms 延迟）
